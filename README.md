# Бот поддержки акции «Вкусная осень»

Тестовое задание на ИИ-инженера (M-Social). Telegram-бот отвечает участникам промо-акции по правилам, вопросы про конкретного участника и всё, чего в правилах нет, передаёт операторам. Веб-панель: очередь обращений, переписка с фото, ответ в бот, закрытие, оценка решений бота, статистика. Бренд, акция и все данные вымышлены.

Стек: PHP 8.4, Laravel 13, PostgreSQL 18, Gemini API, Docker Compose. Локально нужен только Docker.

## Запуск с нуля

Нужен только Docker с Compose v2: Docker Desktop на Windows (поверх WSL2) и macOS, Docker Engine с плагином compose на Linux. PHP и Composer на хосте не нужны.

```
git clone <адрес репозитория> && cd <папка>
cp .env.example .env      # впишите TELEGRAM_BOT_TOKEN и GEMINI_API_KEY
docker compose up
```

Токен бота выдаёт @BotFather в Telegram (команда `/newbot`), ключ Gemini — Google AI Studio (https://aistudio.google.com/apikey). Без ключей проект тоже поднимается: панель работает, а сервис `bot` пишет в лог, какой переменной не хватает; без ключа Gemini бот передаёт все вопросы операторам. Переменные читаются при старте: после правки `.env` перезапустите сервисы (`docker compose restart` или `docker compose up` заново).

Первый запуск собирает образ и ставит зависимости (несколько минут). Когда в логе появится `Server running on [http://0.0.0.0:8080]`, панель доступна на http://localhost:8080. Вход: `admin@example.com` / `password` (меняются в `.env`: `OPERATOR_EMAIL`, `OPERATOR_PASSWORD`). Бот начинает отвечать, как только поднялся сервис `bot` (строка `Бот @… слушает сообщения`).

Всё остальное контейнер делает сам: генерирует `APP_KEY`, выполняет миграции, создаёт первого оператора.

Если порт 8080 занят, впишите в `.env` другой `APP_PORT` и тот же порт в `APP_URL`.

Остановить: `docker compose down`. Снести базу: `docker compose down -v`.

## Команды

Команды проекта выполняются внутри контейнера, проверка на секреты — на хосте (нужен Python 3):

```
docker compose exec web php artisan test          # тесты (на Postgres, база testing)
docker compose exec web php artisan bot:eval      # прогон 25 обращений, отчёт в docs/eval/
docker compose logs -f bot                        # что делает поллер Telegram
docker compose exec web ./vendor/bin/pint         # форматирование
python docs/sessions/tools/check_secrets.py       # перед коммитом: нет ли в файлах токенов и ключей
```

GitHub Actions (`.github/workflows/ci.yml`) на каждый push в `main` повторяет путь проверяющего: `cp .env.example .env`, `docker compose up`, затем тесты и pint внутри контейнера.

`bot:eval` принимает `--now="2026-10-06 10:00"` (часы бота по МСК), `--only=1,9,22`, `--models=…` (цепочка моделей для этого прогона) и `--out=` (путь отчёта). `bot:poll --once` обрабатывает накопившиеся сообщения и выходит, удобно для отладки.

## Как это работает

1. `bot:poll` забирает сообщения long polling'ом (без вебхука), по одному. Дубли от Telegram отсекает уникальный индекс. Номера карт прячутся звёздочками до записи в базу и до отправки в модель.
2. Модель (Gemini) видит правила целиком, текущую дату и календарь розыгрышей (их считает код), последние 6 сообщений и суть открытого обращения. Отвечает строго JSON: действие (`answer` / `operator` / `refuse` / `smalltalk`), текст, суть для оператора, номера пунктов правил.
3. Код проверяет номера пунктов по файлу правил: ответ без существующих пунктов или с выдуманными не уходит, вопрос передаётся оператору. Любой сбой ИИ тоже передаётся оператору: участник не остаётся без ответа.
4. При передаче открывается обращение (у участника не больше одного открытого, остальное дописывается в него), к тексту добавляется фраза о часах работы операторов.
5. Оператор отвечает из панели, ответ уходит в Telegram сразу. Закрытие обращения — с уведомлением участника. Фото участника панель показывает прямо в переписке, подгружая его из Telegram. Модель фото не видит: в Gemini уходит только подпись к нему как обычный текст участника, поэтому надпись на картинке не может стать инструкцией для бота (закреплено тестом). Панель отдаёт файл только как изображение.
6. Каждое решение бота оператор может оценить по шкале из задания (верно / неверно / спорно) и оставить комментарий: на странице «Решения бота» или прямо в обращении. Итоги оценок — в статистике.

Промпты лежат отдельными файлами в `resources/prompts/`. Журнал правок — `docs/prompt-changelog.md`.

## Прогон обращений

Итоговая таблица по 25 обращениям — `docs/eval-report.md`. Там же описано, где бот ошибался и что меняли в промпте. Все отчёты команды `bot:eval` лежат в `docs/eval/`, версия промпта печатается в каждом; имя файла отчёта — время запуска по UTC, внутри отчёта время московское. Таблица собирается скриптом `docs/eval/tools/make_report.py` из отчёта и оценок с комментариями в `docs/eval/tools/verdicts.py`; скрипту нужен Python 3 на хосте, для запуска проекта он не требуется. Отчёты в `docs/eval/`: `2026-10-01_0043.md` — первый прогон (промпт v1), `partial-v2.md` — повтор №9, 12, 17, 18 после правки промпта, `2026-10-01_1044.md` — итоговый (v2), `2026-10-01_1330.md` — проверочный при исчерпанной квоте (по действию 24 из 25: №13 на `gemini-3.5-flash-lite` ответил сам вместо передачи оператору; 20 ответов из 25 дала эта самая слабая модель).

Итоговый прогон (промпт v2, `docs/eval/2026-10-01_1044.md`): действие бота совпало с эталоном во всех 25 обращениях; при чтении ответов 14 «верно», 10 «спорно» (верные по действию и фактам, но без обязательного по эталону элемента), 1 «неверно» (№20: про розыгрыш 13 октября сказано без условия приёма до 12:00). Оценки пересмотрены на финальной проверке перед сдачей по букве шкалы: шесть строк, стоявших как «верно», переведены в «спорно» и «неверно»; шкала и эталон не менялись.

## Допущения

Задание допускает два пути там, где ТЗ молчит: спросить менеджера проекта или принять решение самостоятельно и записать его как допущение. Выбран второй: по каждому открытому вопросу принято рабочее допущение, реализованное так, чтобы при другом ответе правка была в одном месте. Полный список вопросов с допущениями — `docs/questions-for-manager.md`, здесь главные.

| Допущение | Почему |
|---|---|
| Пока у участника открыто обращение, бот сам отвечает на типовые вопросы, а всё, что требует оператора, дописывает в это обращение (вопрос №3 менеджеру) | Задача клиента — разгрузить операторов; типовые вопросы не должны снова попадать в очередь |
| Статистика считается по входящим сообщениям с решением бота: «ответил сам», «передано оператору», «отказ». Приветствия, `/start`, сообщения без текста не считаются (вопрос №1) | Бот отвечает без обращения, а в одно обращение дописываются несколько сообщений: единица счёта — сообщение |
| Среднее время ответа оператора — от открытия обращения до первого ответа оператора, календарные часы (вопрос №2) | Самый простой и честный расчёт; рабочие часы — после ответа менеджера |
| Срок ответа не обещаем, код добавляет часы работы из п. 12.1 (вопрос №4) | SLA в правилах нет |
| При личных вопросах бот просит номер телефона, на который зарегистрирован кабинет; карты, пароли и коды не просит никогда (вопрос №5) | Единственный идентификатор участника по правилам — номер (п. 5.2) |
| Отклонённый чек бот не советует загружать заново: причина — в «Мои чеки» (п. 6.4), возможные причины по п. 6.5, конкретный чек — оператору (вопрос №6) | В правилах не сказано, можно ли повторно зарегистрировать чек, отклонённый из-за ошибки ввода или лимита; неверный совет навредит |
| Чек, оплаченный другим человеком: бот объясняет, что участник и получатель приза — владелец номера (п. 5.2), чек регистрируется один раз (п. 6.2), а само «можно ли» передаёт оператору (вопрос №7) | Прямого ответа в правилах нет, а семейные покупки — частый случай |
| На вопросы вне правил (будут ли акции дальше, сколько участников) бот отвечает той частью, что есть в правилах, остальное передаёт оператору (вопрос №8) | Согласованных ответов (FAQ) нет, а выдумывать бот не должен |
| У модели четыре действия, не три: добавлен `smalltalk` для приветствий и «спасибо» | Иначе по правилу «ответ без пунктов → оператору» такие сообщения уходили бы в очередь |
| Модели Gemini — список `GEMINI_MODELS`; при любом сбое (ошибка, таймаут, квота, кривой ответ) берётся следующая | Бесплатный тариф считает квоту на каждую модель отдельно; так бот живёт дольше |
| Маскирование карт по правилу разработчика: 13–19 цифр подряд с пробелами, дефисами или точками, без проверки Луна. Исключения: российские мобильные номера и реквизиты чека (подпись ФН/ФД/ФП/ККТ или несколько групп цифр длиннее четырёх). Если карта скрыта, код добавляет к ответу просьбу не присылать данные карт | ФН нужен оператору, телефон — ключ к кабинету участника |
| Фото: подпись обрабатывается как текст; фото без текста при открытом обращении прикладывается к нему, иначе бот просит описать вопрос словами. Панель показывает фото, подгружая его из Telegram по `file_id` в момент показа, на диск не копирует | Распознавание фото отложено; копии файлов не нужны, пока файл доступен в Telegram |
| Оценка решения бота хранится в самом решении: одна оценка, последняя побеждает, снятие оценки стирает и комментарий | Оценивается решение, а не диалог; история правок оценки для пилота не нужна |
| Закрытие обращения — с уведомлением участника; автозакрытия нет (вопрос №22) | Без уведомления участник не знает, что вопрос решён |
| Прогон обращений идёт с замороженными часами: вторник 06.10.2026 10:00 МСК; каждое обращение — новый участник без истории | Ответы на №7, 11, 16, 18, 20, 22 зависят от «сейчас»; дата выбрана так, чтобы подвохи с датами сработали |
| Без очереди и worker: поллер обрабатывает сообщения по одному | MVP для пилота; масштабирование — перед продом |
| Первый оператор создаётся из `.env` при каждом старте; пароли базы и оператора по умолчанию заданы в `.env.example` | Проверяющий поднимает проект одной командой; перед продом пароли нужно сменить |
| Ответы бота уходят обычным текстом, без разметки | Звёздочки маскирования и символы участников ломают Markdown |
| Операторы — стандартная таблица `users` Laravel | Участники не входят в панель, своя таблица «пользователей» не нужна |
| Очередь: открытые обращения по времени открытия, старые сверху; «ждёт» — время от открытия до сейчас, пока оператор не ответил; «ждут первого ответа» в статистике — открытые без ответа оператора | Операторам важнее всего то, что ждёт дольше всех |
| Общая очередь без закрепления за оператором; у ответа хранится автор, участнику уходит «Ответ оператора:» без имени (вопрос №20) | Для пилота операторов мало; закрепление — доработка |

## Что не сделано и известные проблемы

Не сделано осознанно, для пилота: распознавание чеков по фото (оператор смотрит фото сам), очередь и повторная доставка сообщений, лимит попыток входа в панель, праздники в часах операторов, фильтр мата и блокировки участников. Подробности ниже и в разделе «Что доработать перед продом».

- **Квота Gemini.** На бесплатном тарифе каждая модель даёт около 20 запросов в сутки (сброс в 10:00 МСК). Один прогон 25 обращений расходует больше, чем квота одной модели, поэтому в `GEMINI_MODELS` цепочка из 7 моделей, и часть ответов в прогоне даёт более слабая модель. Для стабильной работы и для доработки промпта нужен ключ с нормальной квотой (платный тариф или ключ от заказчика). Когда квота всех моделей исчерпана, бот честно передаёт вопросы оператору. В день итогового прогона `gemini-3.8-flash` и `gemini-3.7-flash` к тому же часто отвечали 503 «high demand», и 9 ответов из 25 дала `gemini-3.5-flash-lite`.
- **Ответы неполны там, где эталон требует деталей.** В итоговом прогоне 10 ответов из 25 оценены «спорно» и 1 «неверно»: действие совпало с эталоном во всех 25, но в ответах нет части обязательных элементов (МСК у сроков, условие приёма до 12:00 для будущего розыгрыша, количество призов, оговорка про налог с йогуртницей, частичный ответ по правилам перед передачей оператору). Шесть из них дала `gemini-3.5-flash-lite`, но пропуск МСК есть и у `gemini-3.8-flash`. Разбор — в `docs/eval-report.md`, кандидаты в промпт v3 — в `docs/prompt-changelog.md`.
- **Промпт содержит разборы подвохов из эталона.** В `resources/prompts/system.md` три примера совпадают с обращениями №10, 11 и 18 из задания (7 йогуртов и 2 творожка; второй сертификат; чеки от 27 сентября). Прогон на этих 25 обращениях проверяет и подсказки, а не только модель; на новых вопросах качество может быть ниже. Заменить примеры и перепрогнать — кандидат в v3.
- **Маскирование карт — эвристика.** Российские мобильные номера («+7 910…», «8 910…») и реквизиты чека (подпись ФН/ФД/ФП/ККТ рядом с числом или несколько групп цифр, среди которых есть длиннее четырёх) не трогаются; всё остальное из 13–19 цифр считается картой. Одинокие 16 цифр без подписи (например, ФН без слова «ФН») будут скрыты; городской телефон с кодом в 13 цифр подряд — тоже. Обратные случаи, найденные на финальной проверке: номер, записанный группами не по 4 цифры («22001234 56789012»), и номер, перед которым через пробел стоит другое число из 4+ цифр («код 1234 2200…»), принимаются за реквизиты чека и не скрываются; подпись «ФН» в пределах 12 символов перед номером карты тоже отключает маскирование.
- **Задержка при сбоях моделей.** Поллер обрабатывает сообщения по одному, а цепочка из 7 моделей с таймаутом 60 с каждая и ожиданием до 30 с при минутном лимите в худшем случае отвечает больше десяти минут, и это время ждут все участники.
- **Повтор после падения поллера.** Offset сохраняется после обработки: если процесс упал посреди неё, Telegram пришлёт сообщение снова, и бот дообработает его, потому что решения по нему ещё нет. Если падение случилось между отправкой ответа и записью решения, участник получит ответ дважды.
- **Фото.** Бот не оценивает чеки по фото, оператор смотрит их сам. Картинка подгружается из Telegram при каждом показе: если файл там недоступен (сменился бот, файл удалён), вместо фото будет ошибка. Сообщения с фото без `file_id` (записи, сделанные до появления этой колонки) показываются пометкой «[фото]».
- **Доставка без повторов.** Если Telegram не принял ответ, решение бота записано, но участник ответа не получит; повторной отправки нет.
- **Фраза о сроке ответа без праздников и без даты.** Код называет только часы работы операторов (допущение №4), дату ответа не считает, 4 ноября не учитывает; дополнительные проверки №46–47 в эталоне ждут дату.
- **Ответы модели не детерминированы.** Один и тот же вопрос в разных прогонах может получить немного разный ответ; таблица прогона — снимок конкретного запуска.
- **Ответ оператора без очереди.** Если Telegram принял ответ, а запись в базу не удалась, участник ответ получил, но в панели его не видно. Без очереди это не закрывается.
- Нет лимита попыток входа в панель; `APP_DEBUG=true` по умолчанию (локальный запуск); панель слушает на всех интерфейсах хоста, то есть видна в локальной сети, и работает на встроенном сервере PHP (`php artisan serve`, четыре воркера) — это сервер для разработки. Длинные входящие тексты на странице решений не обрезаются.
- На Linux-хосте файлы, которые создаёт контейнер в папке проекта (`bootstrap/cache`, `storage`, отчёты в `docs/eval/`), принадлежат root: контейнер работает от root. На Windows и macOS это незаметно.

## Что доработать перед продом

- Платный ключ LLM с запасом по квоте; мониторинг доли сбоев ИИ и срабатываний проверки пунктов.

- Вебхук вместо long polling, HTTPS, панель за VPN или с ограничением по IP, лимит попыток входа, двухфакторный вход для операторов.
- Рантайм: nginx + php-fpm вместо встроенного сервера `php artisan serve`, код внутри образа без `composer install` на каждом старте и без dev-зависимостей, запуск не от root, `APP_ENV=production`.
- Персональные данные: минимизировать то, что уходит во внешний ИИ (телефоны, e-mail), срок хранения переписки по п. 11.1 и команда очистки, ответ на запросы об удалении. Трансграничная передача — согласовать с юристами.

- Несколько операторов: закрепление обращения, роли, статистика по операторам; рабочие часы и праздники в статистике.
- Интеграция с сайтом акции (статусы чеков, призы), чтобы бот закрывал и личные вопросы.
