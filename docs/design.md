# Дизайн MVP «Вкусная осень»

Статус: согласовано 01.10.2026 после упрощения. Подробный черновик с вариантами и обоснованиями лежит в истории git (коммит `4c14392`). Здесь только то, что делаем.

Главный принцип: путь наименьшего сопротивления. Умолчания Laravel, минимум сервисов и таблиц. Всё, что убрано, перечислено в конце и попадёт в README → «Что доработать перед продом».

## 1. Запуск

Для проверяющего три действия:

```
cp .env.example .env      # вписать TELEGRAM_BOT_TOKEN и GEMINI_API_KEY
docker compose up
```

Панель: http://localhost:8080, вход `admin@example.com` / `password` (значения из `.env.example`, их можно поменять).

Сервисы `compose.yaml`:

| Сервис | Что делает |
|---|---|
| `postgres` | `postgres:18-alpine`. Healthcheck `pg_isready`. Скрипт в `docker-entrypoint-initdb.d` создаёт вторую БД `testing` для тестов |
| `web` | Entrypoint: если `APP_KEY` пуст — `key:generate`; `migrate --force`; `db:seed --force` (первый оператор из `.env`); `php artisan serve` на 8080. Healthcheck по `/up` |
| `bot` | `php artisan bot:poll`. Стартует после того, как `web` healthy: миграции уже выполнены |

Образ один: `php:8.4-cli` + `pdo_pgsql intl zip opcache pcntl` + composer. Зависимости ставятся при сборке и живут в named volume `vendor`; код и `.env` — bind mount, поэтому `key:generate` пишет ключ в `.env` на хосте, а отчёты прогона попадают в `docs/eval/`.

## 2. Данные

Пять таблиц: `users` (операторы, стандартная таблица Laravel), `participants`, `tickets`, `messages`, `bot_decisions`. Диаграмма и решения — в `docs/db-schema.md`.

## 3. Конвейер входящего сообщения

`bot:poll` работает синхронно, без очереди: одно сообщение за раз.

1. `getUpdates(offset, timeout=30)`. Offset хранится в кеше (таблица `cache`).
2. Только личные чаты. Участник — `firstOrCreate` по `telegram_user_id`.
3. Текст: маскируем карты (`CardMasker`) → сохраняем входящее. Дубль от Telegram отсекает уникальный индекс `(participant_id, telegram_message_id)`: сообщение пропускаем.
4. `/start` → приветствие из кода. Сообщение без текста (стикер, фото без подписи): при открытом обращении сохраняем пометку «[фото]», иначе отвечаем «опишите вопрос словами». Модель не вызываем.
5. Иначе `DecisionEngine`:
   - `PromptBuilder`: `system.md` + правила целиком + текущая дата и календарь розыгрышей (`PromoClock`, `DrawCalendar`) + последние 6 сообщений + суть открытого обращения, если есть.
   - `GeminiClient`: `generateContent` с `responseSchema`, модели из `GEMINI_MODELS` по очереди при любом сбое.
   - Проверка: `action ∈ {answer, operator, refuse, smalltalk}`; `answer` требует хотя бы один существующий пункт, иначе `operator`; сбой или кривой JSON → `operator` с шаблоном кода.
6. `operator`: открываем обращение (`INSERT … ON CONFLICT DO NOTHING` по частичному уникальному индексу) или дописываем в открытое. К тексту код добавляет фразу о сроке по п. 12.1.
7. Сохраняем решение в `bot_decisions`, ответ в `messages`, отправляем `sendMessage`.

## 4. Контракт с моделью

Ответ модели — JSON: `{action, text, operator_summary, rule_refs[]}`. Промпты отдельными файлами в `resources/prompts/`: `system.md`, `user.md`, `decision.schema.json`. Модель не считает даты: текущую дату, ближайшие розыгрыши и календарь недель даёт код. Пункты правил проверяет код: номера должны существовать в `promo-rules.md`.

## 5. Панель

Blade, вход по сессии (`Auth::attempt`), без Filament, Livewire и npm.

| Страница | Что на ней |
|---|---|
| `/login` | форма входа |
| `/tickets` | открытые обращения, старые сверху, колонка «ждёт с»; переключатель на закрытые; автообновление раз в 30 с |
| `/tickets/{id}` | вся переписка участника; у ответов бота — действие и тексты процитированных пунктов; форма ответа (уходит в Telegram сразу); кнопка «Закрыть» с уведомлением участника |
| `/decisions` | все решения бота: сообщение, действие, ответ, пункты, модель |
| `/stats` | см. ниже |

## 6. Статистика

Из `bot_decisions`: «ответил сам» (`answer`), «передано оператору» (`operator`), «отказ» (`refuse`). `smalltalk` и служебные ответы кода не считаем. Обращения: открыто, закрыто, ждут ответа. Среднее время первого ответа оператора: от `tickets.opened_at` до первого сообщения оператора в этом обращении, календарные часы.

## 7. Время

Приложение и база в UTC, колонки `timestamptz`. `PromoClock` — единственный источник «сейчас»: `now()` подменяется параметром `--now` и в тестах, `msk()` переводит в Europe/Moscow. В базу уходят только UTC-значения; тест проверяет, что московское время не сдвигается при записи и чтении.

`DrawCalendar`: вторники с 08.09 по 03.11 в 15:00 МСК, в розыгрыш попадает неделя пн–вс перед ним, отсечка приёма 12:00; после 23:59 01.11 только главный розыгрыш 10.11 в 15:00.

## 8. Прогон обращений

`php artisan bot:eval [--now=2026-10-06T10:00+03:00] [--only=1,9,22]`: 25 обращений из `docs/assignment/requests.md`, каждое как новый участник без истории; действие бота сравнивается с таблицей `docs/expected-answers.md`; отчёт в `docs/eval/<дата>.md` в формате таблицы для сдачи.

## 9. Ловушки

- `env_file` в compose не используем: пустой `APP_KEY` из окружения контейнера перекрыл бы значение из `.env`.
- `.env` читают два парсера: compose раскрывает `$VAR`, phpdotenv — только `${VAR}`. Значения с `$` пишем в одинарных кавычках.
- Файлы задания и промпты могут быть в CRLF: приводим к LF перед разбором.
- Bind mount с Windows медленный, поэтому `vendor` в томе.
- Второй poller с тем же токеном → Telegram отвечает 409.
- Токен бота есть в URL запросов: ошибки HTTP-клиента оборачиваем, URL в логи не пишем.

## 10. Отложено: README → «Что доработать перед продом»

Очередь и worker; повторы доставки и статусы сообщений; лимит попыток входа; рабочие часы и праздники в статистике и во фразе о сроке; распознавание и просмотр фото чеков; фильтр мата и блокировки; удаление данных по п. 11.1; интеграция с сайтом акции; приём писем; несколько операторов с закреплением; перезапуск poller по памяти и обработка 409; HTTPS и публикация панели не только на localhost.
